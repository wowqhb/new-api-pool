# SOP：故障响应

## 角色

- **IC（Incident Commander）**：值班，第一响应人，全程指挥
- **CL（Communications Lead）**：负责状态页 / Telegram / 用户邮件
- **TL（Technical Lead）**：实际修问题的人

P0 必须三个角色齐到岗，P1+ IC 即可。

## 时间轴

```
T+0   告警触发
T+1   IC 确认 (5 分钟内)
T+5   状态页公告（"调查中"）
T+15  初步评估（影响范围/根因方向）
T+30  第一次进展更新
T+60  恢复或重新评估（升级 P 级）
T+x   状态页"已恢复"
T+24h 事后复盘（RCA）
T+7d  改进项落地
```

## 响应流程

1. **告警来了** → IC 看 [`runbooks/`](../runbooks/) 找对应场景
2. **5 分钟内** → 状态页 + Telegram 频道发"调查中"公告
3. **按 runbook 操作** → 不要"创新"，按既定流程
4. **每 15 分钟** → 在内部群里 update 进展（哪怕没进展）
5. **恢复后** → 状态页改"已恢复"，告诉用户具体影响时段
6. **24h 内** → 写 RCA（Root Cause Analysis），归档到 [`postmortems/`](../postmortems/)
7. **1 周内** → 改进项落地（PR / 配置变更 / SOP 更新）

## RCA 模板

```markdown
# RCA: <故障简短描述>

## 概要
- 时间：YYYY-MM-DD HH:MM ~ HH:MM (UTC+8)
- P 级：P0/P1/P2
- 影响范围：<受影响用户数 / 服务 / 时长>
- 根因：<一句话说清>

## 时间线
- HH:MM 告警触发
- HH:MM IC 确认
- HH:MM 公告发布
- HH:MM ...
- HH:MM 恢复

## 根因分析
- What：发生了什么
- Why：为什么会发生（5 个为什么往下问）
- 直接原因：
- 根本原因：

## 影响
- 用户影响：<多少用户 / 多长时间 / 多少请求失败>
- 财务影响：<退款 / 信用损失 / 重购成本>
- 名誉影响：<工单 / 媒体 / 用户群反应>

## 处置过程
- 哪些步骤有效
- 哪些步骤浪费时间
- runbook 是否覆盖到了这个场景

## 改进项 (Action Items)
- [ ] AI-1: <监控盲点>，截止 YYYY-MM-DD，负责人
- [ ] AI-2: <runbook 补充>
- [ ] AI-3: <自动化修复>

## 经验教训
- 我们做对了什么
- 我们做错了什么
- 系统性问题（如果有）
```

## 升级路径（P 级动态调整）

故障实际比初判严重 → 升级 P 级：

- P2 → P1：影响 > 10% 用户 / 持续 > 30 分钟
- P1 → P0：核心通路全挂 / 数据丢失风险 / 安全事件

升级时 IC 要：
1. 立刻 @ 主管（不分时间）
2. 拉更多人进战时频道
3. 公告升级（可能要电话/短信通知 VIP 用户）

## "Don't" 清单（紧急时不能做）

- ❌ 不要在告警群外讨论故障（信息散乱）
- ❌ 不要急着改代码（先恢复服务）
- ❌ 不要瞒着用户（透明度比"完美"重要）
- ❌ 不要事后追责（搞 blameless）
- ❌ 不要把演练和真实故障混（演练时全员要明确知道）
